# PFSpec 4090D 正式结果分析

日期：2026-10-29。原始数据包：`PFSpec_Formal_4090D_Review_20261029.tar.gz`。数据来自 RTX 4090D 正式运行的 A、B 记录与实际运行脚本。

## 运行范围与口径

A 比较 Target、优化 Target、Position-only、W1 和 W1+Rescue：30 个场景，120 个固定输入、60 个真实前缀补全、30 个 BOS 起始输入；每种方法共 210 个请求。固定生成上限为 512 token，自然生成上限为 16000 token，KV 缓存容量为 16384。B 在 120 个固定输入上比较 W1 与 W2。运行采用 FP32、TF32 关闭、temperature 0.9、top-p 0.9。

生成吞吐按实际生成 token 数除以同步计时的生成时间；端到端时间从准备好的 prompt 开始，包含生成、VQ 解码、Gaussian 导出和六张 384×384 PNG 保存，不含模型加载和预热。加速倍率按同一 prompt、seed 和场景配对，先对来源内的对数倍率取平均，再以来源为单位做 5000 次 bootstrap，给出 95% 区间。倍率大于 1 表示表中前项更快。

W1 相对 Target 和优化 Target 在三种请求场景的生成吞吐均有增益；这些数值不能直接解释为完整请求时间倍率。Position-only 相对优化 Target 的生成吞吐也有增益。W1 相对 Position-only 的额外收益只在固定输入明显；BOS 起始输入中 W1 慢约 5%，真实前缀补全中差异区间跨过 1。

自然 BOS 和真实前缀两组中，各方法 90/90 请求均以 EOS 结束，没有触及 16000-token 上限。固定组部分请求提前 EOS：Target 与优化 Target 各 7/120，Position-only 5/120，W1 和 Rescue 各 4/120。各方法平均生成长度不同，性能比较已用实际生成 token 数计算。

## 完整请求时间倍率

这些配对倍率使用参考方法完整请求时间除以 W1 完整请求时间；95% 区间按场景或 BOS 种子重采样 5000 次。它与端到端 token 吞吐倍率在生成长度不同时可以不同。

| 输入 | W1 / 优化 Target 时间倍率 | 95% 区间 | W1 / 原 Target 时间倍率 |
|---|---:|---:|---:|
| 固定 512 | 1.371 | [1.258, 1.478] | 4.036 |
| 自然 BOS | 1.278 | [1.153, 1.418] | 3.695 |
| 自然补全 | 1.006 | [0.741, 1.329] | 2.824 |

自然补全相对优化 Target 的时间优势尚未确立。复算脚本使用固定随机种子；区间端点与采用其他随机种子的重采样可能略有差异。详细计算见 `analyze_request_wall.py` 与 `request_wall_metrics_20261029.json`。

## P/F 机制与计算成本

Position 接受比例与 Feature 分支命中比例不同；两者条件分母不同，不能直接比较预测难度。W1 的计数汇总如下。Feature 分支接受率按 `feature_branch_hits / (feature_branch_hits + feature_all_rejected)` 计算。

| 场景 | Position 验证数 / 提议数 | Position 接受数 / 验证数 | Feature 分支命中率 | W1 相对 Position-only 的 Target 调用变化 | Target 输入 token 变化 |
|---|---:|---:|---:|---:|---:|
| 固定 512 | 65.0% | 91.9% | 32.9% | −20.4% | +40.7% |
| BOS 起始 | 60.4% | 93.2% | 22.4% | −17.2% | +61.6% |
| 真实前缀补全 | 61.2% | 92.3% | 24.3% | −15.7% | +59.1% |

W1 的 P/F 候选减少了 Target 调用轮数，却扩大每次验证要处理的树节点与 Target 输入 token。固定输入中这笔额外计算带来吞吐收益；自然 BOS 中 Feature 命中约 22%，Target 输入 token 比 Position-only 多 61.6%，与生成吞吐下降同时出现，具体成本归因仍需逐轮测量。真实前缀补全的净倍率接近 1。数据支持 P/F 两类 token 的接受行为不同，也显示当前 Feature 分支成本较高；不能据此主张 Feature MLP 在自然生成中优于 Position-only。

### Rescue 的独立收益

| 场景 | Recovery 调用变化（Rescue 相对 W1） | Target 调用变化 | Target 输入 token 变化 | Rescue / W1 生成倍率 | Rescue / W1 端到端 token 吞吐倍率 | 输出及语义计数相同 |
|---|---:|---:|---:|---:|---:|
| 固定 512 | −34.7% | −3.3% | +7.6% | 1.012 | 1.012 | 120/120 |
| BOS 起始 | −48.5% | −3.6% | +10.3% | 0.984 | 0.985 | 30/30 |
| 真实前缀补全 | −47.3% | −4.0% | +11.3% | 0.993 | 0.993 | 60/60 |

Rescue 在三种场景都保持 W1 的输出和主要语义动作计数，但没有稳定的时延收益：固定输入约快 1.2%，两种自然输入约慢 0.7%–1.6%。它确实减少 recovery 次数，却增加 Target 输入 token；目前适合作为保持输出等价的执行路径优化，独立加速贡献较弱。

### W2 的成本

B 中 W2 的候选树节点为 43026，W1 为 23277（约 1.85 倍）；Target 树节点为 129078 对 93108（约多 38.6%）；Target 输入 token 为 150835 对 114949（约多 31.2%）。W2 的 Target 调用少 7.1%，Feature 接受数多 19.3%，但生成吞吐仍低 3.1%，端到端吞吐低 2.6%。该宽度下额外分支的验证与生成吞吐下降同时出现，具体成本归因仍需逐轮测量。

## OOM 续跑与计时敏感性

A 首轮在 `bos-68220` 的 VQ-VAE 稀疏 Gaussian 解码步骤遇到 CUDA 分配失败，保留了 995 条记录。相同 Rescue 请求在单方法新进程重放成功，得到 295529 个 Gaussian，峰值分配显存约 3.58 GiB。之后重跑 11 个未完成 BOS 请求组，A 合并为 1050/1050；B 为 240/240。归档保留首轮、续跑和 `merge_sources.json`。

11 个重跑组占自然 BOS 样本的 11/30，且在新进程中创建运行图。按是否续跑拆开计算 W1/Target 点估计：首轮 19 个 BOS 的生成倍率 3.735、端到端 3.577；续跑 11 个分别为 3.790、3.615；合并后为 3.755、3.591。点估计接近，但两个子集较小，且运行图冷热状态不同，论文应报告该敏感性，不要把整组当作同一运行状态。

失败发生在 VQ-VAE 解码而非 token 生成；单方法重放通过，指向正式多方法进程的显存压力。失败瞬间没有独立 GPU 显存采样，不能精确还原剩余显存和碎片状态。

## 论文证据判断

- **生成吞吐：有正式支持。** W1 相对原 Target、优化 Target 的生成吞吐来源配对区间在三种场景均高于 1。自然补全相对优化 Target 的完整请求时间倍率区间包含 1。
- **Position-only 贡献：有正式支持。** 相对优化 Target，三种场景分别约 1.35–1.39 倍生成吞吐。
- **P/F 异构接受行为：有正式支持。** Position 接受率约 92%–93%，Feature 分支命中率约 22%–33%。两项统计的条件分母不同；W1 相对 Position-only 的自然生成增益未获支持，Feature 分支的计算成本是核心限制。
- **Rescue：输出等价得到 210/210 组支持；稳定独立提速没有得到支持。** recovery 调用减少，但端到端倍率靠近 1 且场景方向不一致。
- **W2：当前宽度 2 方案没有吞吐收益。** 固定组配对区间低于 1。
- **完整三维生成：流程有效性得到支持，画质提升没有得到支持。** 7740 张视图完成保存；缺少真实场景真值和 FID/PSNR/SSIM 等质量度量。

30 个场景来自作者 3D-FRONT 验证清单，选取时排除了已记录的历史使用来源和作者训练集场景组。现存记录无法证明它们没有出现在作者 Target 预训练数据或其他未登记开发活动中。实验结论限于当前 GaussianGPT 权重、4090D 和这 30 个场景。
