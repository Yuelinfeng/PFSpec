# 空间模型在线速度结果独立复算

本次仅用 Python 标准库读取 `raw/run01/records.jsonl`，逐行重新计算运行数、计数、输出长度、EOS、配对吞吐比和来源方向。汇总数字与 `PRIMARY_VALIDATION.json` 一致；未重新抽样计算置信区间。独立复算未读取更早轮次的 Target 速度。

## 范围与完整度

`raw/run01/pipeline.json` 记录任务完成，180 次运行用时 936.744 秒，低于 1800 秒总额度。记录包含 60 个完整配对组、10 个既有开发来源、64/256 Token 两种前缀和三个种子；每个方法各 60 次。硬件为 RTX 4090，FP32 最高精度，TF32 关闭，temperature=0.9、top-p=0.9。

同轮 Target-only、原 PF-K2 和空间 S3 的输出长度如下：

| 方法 | 512 Token | 较早 EOS | 其他长度 | 输出 Token 总数 |
|---|---:|---:|---:|---:|
| Target-only | 60 | 0 | 0 | 30,720 |
| 原 PF-K2 | 58 | 2 | 51、75 各 1 次 | 29,822 |
| 空间 S3 | 60 | 0 | 0 | 30,720 |

三个方法共同输出满 512 Token 的配对组有 58 组，覆盖全部 10 个来源。主比较只用本轮同一来源、前缀和种子的成对记录；Target-only 数字也来自这 60 组，没有混入旧轮次数据。

## 结论与限制

在这组固定条件下，空间 S3 的 Feature 接受率略高，但总吞吐低于原 PF-K2；共同满长度子集也更慢。来源区间位于 1 以下，当前记录不支持空间 S3 带来额外速度。若后续要提高速度，需减少逐次邻居构造、统计处理及残差模型带来的开销；本轮没有测量这些部分的单独耗时，也没有试验新的优化实现。

这 10 个来源此前已用于开发，不代表独立来源结果；区间按来源重采样，没有传播同一来源内不同种子和前缀的计时波动。矩阵只覆盖两个前缀、三个种子及最多 512 个新 Token。输出长度和自然 EOS 已计入记录，但本轮没有做独立生成质量或三维质量评价。因此结果适合判断当前实现是否值得继续做速度优化，不足以说明其他数据上的速度或生成质量。
