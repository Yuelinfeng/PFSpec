# PFSpec：技术差异与创新性论证

2026-10-27。范围：现有解码源码、已保存的实验元数据与结果，以及最接近论文的相关方法段落。本轮没有新增算法、训练或性能实验。本文补充机制与证据对照，不继续改写 Introduction。

## 1. 结论

现有材料已支持 PFSpec 的具体实现有效，以及若干组件和恢复复用具有增量价值；尚不足以判断论文的主要问题只是创新性解释不充分。已有技术的组合与针对 P/F 的有价值计算设计，两种审稿解读仍然成立。

**主比较有意让 W1 与 Feature EAGLE 适配版采用同一个 Position Ranker。** 作者明确说明，其目的是先用位置投机获得有效的加速起点，再评价不同 Feature 预测与状态维护能否保留并扩大这项收益。共享 Ranker 因而是具有明确目的的对照设计。该目的与归因边界同时成立：两者的速度差评价完整 P/F 路径的增量，不能作为“类型化方案优于不理解 P/F 的统一草稿”的证据，也不能全部归给单个状态预测器。

目前最具体、可由代码支持的主张是：**W1 利用位置历史直接提出两个 Position，在中间的 Feature 上进行一次状态预测，构造不需要逐 token 维护神经草稿状态的短路径；Target 仍按完整条件历史验证。** Rescue 随后处理这一参考流程中剩余的第一 Position 恢复工作。

这一计算安排具有明确对象和可解释作用。其跨方法优势与创新幅度仍需区别于“所用原语已有先例”“当前配置运行更快”这两项事实。

## 2. 具体改变了什么计算

令已生成历史为 \(H=(\ldots,P_i,F_i)\)，\(H_P\) 为位置历史，\(u_i\) 为 Target 在 \(P_i\) 后的隐藏状态。W1 开始时 \(F_i\) 已输出，但尚待送入 Target。完整候选轮的提案为：

\[
a=R(H_P),\qquad
c=R(H_P\oplus a),\qquad
\widehat u_a=u_i+g_\phi(u_i,F_i,a),\qquad
f\sim q_F(\cdot\mid\widehat u_a).
\]

其中 \(g_\phi\) 的输入编码省略不写；Feature 分布仍经过共享 Target 归一化、输出头及实际采样处理。当前代码在调用 Feature 预测器之前，已经选好 \(a,c\)。因此可将主路径的实际提案写为

\[
q(a,f,c\mid H)
=\delta_{R(H_P)}(a)\,
q_F(f\mid u_i,F_i,a)\,
\delta_{R(H_P\oplus a)}(c).
\]

**这一式子描述草稿的计算选择。Target 的完整条件依赖保持。** Target 对第二 Position 的验证仍使用 \(p_P(c\mid H,a,f)\)。位置排序没有读取候选 Feature，并不说明真实位置分布与 Feature 无关。标准接受与残差采样允许使用这种近似提案。

| 计算对象 | W1 的实际安排 | 与逐 token 状态草稿的关系 |
|---|---|---|
| 第一 Position \(a\) | 位置历史上的合法候选排序 | 位置候选不需要神经草稿先预测 pending Feature 后的完整状态 |
| 候选位置后的状态 \(\widehat u_a\) | 从已有 Target 状态及两个 token 条件直接预测 | 不在草稿中依次建立 pending Feature 状态和候选 Position 状态 |
| 第二 Position \(c\) | 在加入 \(a\) 的位置历史上继续排序 | 不依赖候选 \(f\) 的神经状态计算 |
| 下一轮 Feature 起草 | 使用本轮实际提交路径的 Target 状态 | 预测出的草稿状态不作为下一轮的递归起点；仍保留 Target KV 和 Ranker 在线状态 |
| 第一 Position 恢复 | 单备用命中时复用 Target 条件状态 | 不改变 W1 的主接受与残差采样，代价是新增验证节点 |

代码依据：[位置提案及 W1/Rescue 控制流程](../../../../patches/spec_next_20261022/position_rescue_decoder.py)、[已保存的 Feature 模型定义](../position_transition_20261020/source_before/train_feature_state_distill.py)、[Feature 调用接口](../position_transition_20261020/source_before/draft_a/pf_feature_unified.py)。上述事实支持具体计算图的区别，不单独证明成本最优或新颖性。

## 4. 共享 Ranker 的实验目的与结果解释

作者补充的实验目的为：将 Position Ranker 提供的位置投机收益作为共同起点，判断不同 Feature 草稿能否在此基础上取得净增量。正文采用“已测设置下有效的加速起点”表述这一经验依据，不将其写成任意输入、设备或附加草稿下的速度下界。

[主测元数据](../pf_comparison_20261025/main_run01/plan.json) 将本地 v3 标记为 `mode=feature`、`gamma=3`、`reuse_draft_cache=False`；v4 对照使用相同权重并开启 Draft KV 复用。[已保存适配器](../../../../patches/feature_tree_20261021/reference/method_adapters.py) 在 feature 模式向解码器传入同一 Ranker；[本地解码器源码](../../../../patches/eagle_pf_v2/speculative/pf_engine.py) 的 PositionRanker 将该选择转成点提案。

Position-only/优化 Target 为 1.395117×，W1 为 1.551487×，对应在位置投机上约 11.2% 的额外吞吐；当前 Ranker + EAGLE 式 Feature 草稿为 0.966838×。因此，最直接的实验结论是：W1 的 Feature 预测与后续推进扩大了已有位置收益，当前 EAGLE 适配配置的额外工作则未能保留该收益。无需为解释这一设计而把 EAGLE 对照描绘成不使用 P/F 信息的方法。Medusa/Hydra 是另外的完整适配方法对照，未因此获得相同 Ranker。本地 v3/v4 是项目适配版本号，不对应官方 EAGLE-3 的论文版本。

共享位置提案机制不等于所有方法经历相同的位置轨迹。Feature 输出会影响 Target 的后续条件分布和实际接受结果，从而改变各方法到达的历史。因此，这是一组完整路径收益比较，不能把 Position-only 的倍率作为可与任意 Feature 收益直接相加或相乘的固定量。

本地解码器在起草阶段准备草稿历史，并逐 token 更新预测状态；W1 的 MLP 路径没有这套独立神经草稿历史缓存。还应注意一处具体执行差异：在所读 `gamma=3` 的 P/F/P 路径中，Feature 后仍调用一次草稿状态更新，而下一 Position 由 Ranker 选择；该更新的输出不参与本轮新的 Feature 分布预测。非复用版本下一轮重新准备草稿缓存，因此不能把这项工作视为所有 EAGLE 适配都不可避免的成本。此项来自本地代码控制流程，未重新运行对应配置，也没有测得该调用对主测时间的独立贡献。

现有比较还同时改变了训练、状态归一化、预测误差和轮次控制。当前总时间差不能拆成“省去状态更新带来的纯收益”。这是科学归因限制，本轮没有据此修改实现或安排新实验。

## 6. 最合适的创新性回答

PFSpec 的具体技术价值在于：利用合法位置历史承担位置提案，将神经状态预测集中于 Feature 所需的候选位置状态，从而构造一条省去部分逐 token 草稿状态工作的 P/F 短路径；Target 保留完整条件依赖和原采样规则。对该参考流程的进一步分析表明，位置拒绝后的部分条件状态还可以在同次验证中提前获得，并在原残差采样命中时复用。

这个回答给出了实际输入、计算对象和输出状态，能够区别于泛泛的“将投机解码应用于 GaussianGPT”。它仍属于现有投机解码框架内的特定计算设计：候选条件化、状态预测、树验证、分布保持和命中复用均有先例。论文需要通过实现及机制证据说明这一选择值得研究，不要求证明通用框架不能表达它，也不应预先把“只有这一设计有效”作为结论。

针对作者设定的完整路径增量问题，现有 Position-only、W1 和 EAGLE 适配结果已经提供直接证据。若进一步主张优势专门来自某种状态计算安排，仍需注意：当前尚未在足够匹配的 Position 提案、条件信息、验证安排和训练条件下，隔离“逐 token 草稿状态推进”与“P/F 短路径状态预测”的净差异。B0/B1 已完成的是同一 W1 内的预测器比较，当前 EAGLE 对照则还有多项差异。此处只说明缺口，不据此新增模块或自动启动实验。

关于适用性，已有主结果覆盖 30 个来源，另有 20 个新来源上的恢复机制记录，不能概括为只在单个场景有效。限制应具体表述为：主要完整方法仍在一个 Target 和一类设备上评价；新来源恢复增量不能代替完整方案跨模型、跨表示与不同请求长度的证据。[新来源恢复记录](../recovery_value_20261023/RESULTS.md)
