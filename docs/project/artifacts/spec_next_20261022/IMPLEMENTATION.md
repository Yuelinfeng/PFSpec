# 两个新候选的实现

本轮沿用静态 W1 的 Target、Ranker、MLP 权重、FP32 设置与采样温度/top-p 0.9。所有代码位于 `patches/spec_next_20261022/`，生产默认值保持原状。

## 备用 Position 节点

原 W1 一次验证四节点 `[pendingF,P1,F1,P2]`。若 Ranker 提供多个合法位置，新候选增加一个次高分位置 P1b，节点为 `[pendingF,P1,F1,P2,P1b]`，父节点依次为 `[-1,0,1,2,0]`，逻辑深度为 `[0,1,2,3,1]`。第五行输出 P1b 后的 Feature logits。

先照原 W1 接受或拒绝 P1。拒绝时仍从原点提案残差分布抽实际位置，保持随机数消耗顺序。实际位置等于 P1b 时保留路径 `[0,4]`，使用第五行 logits 抽 Feature，并使用第五行 hidden 继续下一轮；因此省一次恢复前向。其他位置按原方式恢复。只有一个合法候选时使用原四节点运行时，K1 尾步也沿用原逻辑。

给定首候选 a 和备用 b，p(a)<1时备用命中的无条件概率为 `(1-p(a))·p(b)/(1-p(a))=p(b)`；p(a)=1时两者均为零。该恒等式说明哪些已算结果可复用，不能直接给出速度收益。额外节点在每个适用轮次都产生成本，命中才节省恢复。

原 `position_accepted` 计数保持原接受定义。另记备用节点、拒绝与 `position_rescue_hits`，不把备用命中混入原接受率。正式源码移除了逐轮读取备用 Target 概率的额外诊断操作，主测只保留命中计数。

## 上一处 Target Feature 分布复用

记 MLP 提案为 q，上一已提交位置处已计算的 Target Feature policy 为 s，本轮提案为 `q_mix=0.75q+0.25s`。混合后不再做 top-p；接受比值与拒绝残差均使用实际 q_mix。s 来自本轮提案前的历史，当前轮尚未计算的 Target policy 不进入本轮 q_mix。

每个请求独立保存 s，更新时序如下：

| 已确认的实际位置 | 为下一轮保存的 Feature policy |
|---|---|
| 非空前缀的末尾 Position | 前缀计算的最后一行 |
| BOS 后首个 Position | 普通 Target 计算的 Feature 行 |
| P1 接受，无论 F1 是否接受 | W1 第二行 |
| P2 接受 | W1 第四行 |
| P1 或 P2 拒绝且实际位置非 EOS | 实际位置恢复前向的 Feature 行 |
| K1 完成一个实际位置 | 该实际位置对应的 Feature 行 |

缓存跟随实际路径更新，不使用未接受位置的分布。请求结束后释放；权重为 0 的分支沿用原 W1 的操作与随机数顺序。主版本使用独立概率副本，额外的 fast 备选使用 `torch.lerp` 与已生成概率张量的切片来减少小向量操作；fast 已完成393次GPU概率比较，支持集相同、最大半L1为1.851004e-8；不能将其实数表达式相同理解为FP32逐位相同。

混合提案继续使用标准的 `min(1,p(y)/q_mix(y))` 接受律和归一化 `(p−q_mix)` 正部抽样。这允许 q_mix 在任意合法 Feature 支持上分配概率。该规则是既有投机解码的精确采样方法，本轮研究的是利用已计算概率信息改善提案，未提出新的通用采样定理。

## 已完成的正确性验证

概率化 Position 的小词表枚举覆盖支持集不完整、EOS、单候选和 q=p；混合 q 的多个权重也满足输出概率等于 Target，最大绝对误差约 5.6e-17。该方案的初始接受率诊断没有改善，未扩大其完整速度矩阵。

GPU `candidates_verify_run01` 完成八来源十三个真实前缀、78 个 logits/hidden 对照，以及十三条备用路径 KV 提交对照。策略支持集一致，最大概率 TV=3.640074e-6；hidden/KV 全有限，两项整体相对误差均不超过已有的 2e-6 范围。逐元素 allclose 按张量比较组计有 121/182 组未通过，完整记录保留，未作为逐位相同的证据。

另有 204 次解码：40 组 W1/备用/混合权重零/混合重复，加四次 BOS 路径。输出、语义计数和重放满足相应关系，备用共命中 56 次，恰好省下 56 次恢复。独立标量审计见 `verification_audit.json`；没有保存完整 hidden/KV 原张量，因此该审计没有独立重算原张量误差。尚不对任意前缀、任意窗口或三维质量作外推。

## 计时范围

正式主测各臂拥有独立持久 Target、提案和树运行时；备用臂另有专用五节点图。预热对象丢弃，正式首次建图进入同步外层墙钟。缓存准备、前缀计算、提案、验证、恢复、抽样和末尾同步均计入。权重加载、VQ、渲染与文件输出不进入该 token 生成指标。

## 组合与快速混合实现

`feature_reuse_fast_decoder.py` 使用 `torch.lerp(q_MLP, p_previous, .25)`，保留已分配的 FP32 policy 概率向量的视图。policy 内部先复制并过滤 logits，再由 softmax 新建概率张量；抽样与残差使用另外的张量，不会覆盖缓存。不能保留图运行时借出的 logits 视图作为历史值。

`combined_decoder.py` 以备用 Position 解码器为起点，将同样的缓存与 lerp 合入。备用命中后，从第五行抽取实际 Feature，同时保存该 Position 对应的 Feature policy；后续隐状态使用同一行，提交路径为 `[0,4]`。混合权重为零时不执行缓存与混合，沿用原抽样顺序。

组合与快速混合属于 `source_run03`，未改 `source_run02` 开发主测。对应测量入口为 `evaluate_combined.py`；原 `evaluate_candidates.py` 保留原样。组合的抽样枚举与36次GPU对照已通过，跨来源速度结论另见最终结果。
