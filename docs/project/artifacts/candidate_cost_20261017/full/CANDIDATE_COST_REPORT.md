# GaussianGPT 候选的边际计算价值：A1–A3

本轮只测量现有 step12000 轻量 PF 与 P-only，没有训练新 Head。

## 结论与选择

同批不加分项计时的固定窗口 token 生成中，PF/P-only 来源等权速度比为 **1.171× [1.130, 1.211]**。
P₂ 非 EOS 拒绝后的整段处理占少量计时点复测总时长 **1.337%**；把这段处理全部免费删除、其余行为保持原样，时间相减估计为 **1.0136×**。这包含残差采样、KV 回退、Target 补算、状态保存和 Feature 采样，范围大于单独补算前向。
相同前缀的单轮对照中，PF/P-only 来源等权即时推进效率比为 **1.141× [1.085, 1.195]**。该结果只描述当前一轮，不能代替长期策略比较。

当前选择：保留现用 Feature Draft，暂缓以提高 P₂ 接受率为主要目的的独立 Head 训练。若能减少已有提案成本或与 Feature 共享计算，另行比较净时间；本轮未证明新的动态方法已经成立。

## 对象与测量范围

- 原十个开发来源，每个来源首条裁剪，64/256/1024 可用前缀，共 28 个来源与前缀组合。
- 两个运行种子、每次最多 256 个新 token，FP32、temperature/top-p=0.9；使用原 Target、Ranker、step12000。
- 56 次普通 PF、56 次普通 P-only、56 次带分支计时的 PF，方法顺序轮换。
- 56 个相同上下文：28 个真实初始前缀与各自一条 PF 运行的中间前缀；每个上下文 8 个种子，两种策略，共 896 次单轮。
- 单轮对照复用同一解码循环，P-only 停止第二位置提案且不运行 Feature Draft。缓存分配、前缀计算与历史恢复在单轮计时之外；两种策略都从准备完毕的状态开始。
- 固定窗口计时包含缓存分配、前缀计算、提案、验证、拒绝处理与释放；模型加载、预热和 JSON 保存在计时之外。

平均额外推进 0.482 token，额外耗时 1.828 ms。推进量比为 1.241，耗时比为 1.087。收益取决于两者的关系。

| 上下文来源 | PF/P-only 即时推进效率比，来源等权 [95% 区间] |
| --- | --- |
| 真实初始前缀 | 1.059× [1.004, 1.118] |
| PF 运行中间前缀 | 1.208× [1.114, 1.315] |

两类上下文的收益不同，但前缀内容、位置和历史长度也不同，不能据此确定差异原因或直接选定动态策略。相同上下文对照比较的是整个 PF 动作，包含额外位置提案与更长 Target 验证，无法单独归因于 MLP 这一组件。

完整 PF 记录中，F₁ 接受/已验证为 34.42%，每轮 P₁、F₁ 连续接受概率为 30.22%。普通轮次推进量遵循 2+2×连续接受指示量。

Feature 被拒绝时，保留 P₁ 的 Target 状态，残差生成 F₁ 并回退缓存；该分支没有新增 Target 补算。P₁ 被拒绝时，需要补算实际 Position；P₂ 被拒绝且结果非 EOS 时，也需要补算实际 Position。F₁ 连续接受后，额外推进的 P₂/F₂ 来自已算验证结果或拒绝后的补算。

## A2：P₂ 补算成本

P₂ 拒绝 113 次，非 EOS 实际补算 113 次；完整 PF Target 调用 5875 次。原 113 次属于拒绝计数，实际补算次数另列。

| 时间范围 | 累计 host 时间，s | 累计 CUDA event 区间，s |
| --- | ---: | ---: |
| 仅 Target 补算前向 | 1.474480 | 1.477628 |
| 非 EOS 拒绝整段处理 | 1.580256 | 1.580277 |

仅补算前向的 CUDA event 区间占总时长 1.239%；整段处理的 host 时间占比为 1.325%。前向 host 时长未逐次同步，不单独解释成其完整等待时间。
额外 8 次运行在补算前后同步；其中 9 次前向的同步 host 时间累计 0.124221 s，CUDA event 区间 0.124441 s。同步运行仅用于佐证成本量级。

另对全部 56 条 PF 路径复测，只记录每轮及 P₂ 整段处理的起止。整段 host 时间累计 1.552845 s，总时长 116.106823 s，占比 1.337%；对应乐观时间相减为 1.0136×。全部输出与普通运行一致；8 组交错普通运行中，少量计时点/普通运行吞吐比为 0.998×。

现有 P₂ Ranker 提案共 5078 次，CPU 函数时长累计 0.492755 s，占分项计时总时长 0.413%。新 P₂ 模块若替换当前 Ranker，还应比较新旧提案成本；仅凭拒绝补算占比，无法排除更便宜的 P₂ 提案机制。

将可免费删除的处理时间粗略摊到全部 5078 次 P₂ 提案，每次约 0.306 ms。若新增模块每轮都运行，它需要先覆盖自身成本，且真实模型无法保证消除全部拒绝。该数字只用于当前路径的成本量级判断。

免费删除整段处理的数字是已观测路径上的乐观时间相减结果。它省略新提案成本，并假设前缀、输出、接受事件及其他操作都保持原样；不能解释为任意条件 P₂ 方法的全局加速上限。CUDA event 与 host 时间分别使用，不相加。

## 验证与限制

56 组 PF 普通运行与分项运行的输出逐 token 一致；与上一轮同种子记录的关键计数在 56/56 组一致。轮次输出量、Target 调用量与完整记录相符，EOS 短验证通过。
带分项计时 PF / 普通 PF 的来源等权吞吐比为 0.975× [0.969, 0.981]。分项计时增加了开销，正式速度采用普通运行；分支成本占比属于带计时运行。单轮对照仅记录轮次起止，避免逐操作计时影响两种策略的比较。
CUDA event 记录同一流上的时间区间，可能包含 CPU 提交间隙，不等于纯 kernel 活跃时间。P₂ 整段结束前已有采样取值同步；其 host 区间包含该段实际等待。
来源区间按十个开发场景重采样，只反映当前权重和运行设置。中间前缀由 PF 产生；有限重复和上下文抽样不能证明任意长期策略更优。本轮没有新增正式测试或三维质量结论。
