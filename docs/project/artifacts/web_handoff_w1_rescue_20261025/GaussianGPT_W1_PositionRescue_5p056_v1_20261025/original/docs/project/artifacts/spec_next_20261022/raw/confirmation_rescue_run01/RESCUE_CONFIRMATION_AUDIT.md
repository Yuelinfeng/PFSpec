# Rescue 确认批次独立复算

## 结论

五节点备用位置分支在本批中保留了与 W1 完全相同的输出及接受路径。它让 source 等权速度相对 W1 提升 1.75%，全臂跑满 512 token 且无新增图的交集上提升 2.33%。同一批 rescue / 原始 Target 为 5.06×；这主要来自已有 W1 路线，备用分支的增量应看 rescue / W1。

## 数据范围与计算方式

从 `records.jsonl`、`prompts.json`、`plan.json` 和 `pipeline.json` 逐条读取，共 180 条记录、60 个输入配对、30 个来源，每个来源含 prefix 64 与 256，预算 512 token。60 组均包含 target、w1、rescue 各一条；记录中的输出长度与 `generated_tokens` 一致，180 条均标记 `sequence_validated=true`。

吞吐倍率按每来源内配对记录的 log 比值汇总，再对来源等权平均。区间采用来源重采样 percentile bootstrap，10,000 次，seed 402101。生成的两份 JSON 保留每个来源的倍率和各子集结果。置信区间 seed 与主代理另用 seed 104212 的复算略有不同，点估计应相同。

`plan.json` 的 `source_scope` 字段写作 `development`。同目录上一层的 `source_scope_note.json` 说明，该值来自遗漏可选 scope 参数后的默认标签；实际读取路径为 `stage_e_final/final_test_crops.pt`，来源与前一批 confirmation_run01 相同。本批在前一批结果形成后追加，单独报告，没有与前批记录合并。

## 速度结果

表中每格为 source 等权几何倍率及 95% 区间；比较项是左侧方法吞吐除以右侧方法吞吐。

| 配对范围 | 配对数 / 来源数 | rescue / 原始 Target | W1 / 原始 Target | rescue / W1 |
|---|---:|---:|---:|---:|
| 全部配对 | 60 / 30 | 5.0561 [4.5537, 5.3841] | 4.9692 [4.5259, 5.2645] | 1.01748 [1.00252, 1.02693] |
| 三臂均跑满 512 token | 56 / 30 | 5.0951 [4.7417, 5.3449] | 4.9992 [4.6897, 5.2262] | 1.01918 [1.00901, 1.02639] |
| 三臂均无新增图 | 58 / 29 | 5.2939 [5.1737, 5.4128] | 5.1704 [5.0443, 5.2943] | 1.02390 [1.01996, 1.02787] |
| 跑满 512 且三臂均无新增图 | 55 / 29 | 5.2466 [5.1146, 5.3823] | 5.1273 [4.9929, 5.2651] | 1.02327 [1.01908, 1.02734] |

两臂 W1/rescue 自身都有 58 组跑满 512 token；三臂交集为 56 组，因为原始 Target 另有两条提前 EOS。三臂无新增图的 58 组排除了 prefix 64、256 的首次形状准备配对；再与跑满条件取交集后为 55 组。汇总器也将 target 首条 `runtime_created=true` 的配对排除在无新增图集合之外，尽管该条没有 Target 图事件。

## 输出、接受路径与恢复调用

W1 与 rescue 的 60/60 配对逐 token 输出相同，生成长度和 EOS 标记也逐对相同。两臂的接受数组、Position/Feature 接受计数与接受率字段 60/60 一致：Position 共提议 22,725 次、验证 15,086 次、接受 13,903 次；Feature 共提议 11,340 次、验证 10,345 次、接受 3,701 次。Position 验证接受率为 92.16%，Feature 验证接受率为 35.78%，Feature 命中占每次树验证的 32.64%。

rescue 记录中备用节点共 3,875 个，拒绝 858 次，实际救援命中 388 次。W1 的恢复调用为 1,181 次，rescue 为 793 次，差额 388 次；逐配对均满足恢复调用差额等于该配对的 `position_rescue_hits`。这些命中属于拒绝后的恢复路径，未计入 Position 或 Feature 的接受数。

救援分支使 Target 树节点从 45,360 增至 49,235，Target 输入 token 从 56,231 增至 59,718；同时 Target 调用数从 12,626 降至 12,238。也就是说，它增加了树内计算，以 388 次真实命中换掉相同数量的恢复调用。净吞吐变化仍以端到端配对实测为准。

## EOS、图准备与剩余范围

三个方法各有 2 条自然 EOS。Target 的 EOS 输出长度为 23、49；W1 与 rescue 均为 109、365。其余每臂 58 条均生成 512 token，所有 EOS 输出的末 token 都是计划中的 EOS id 12096。Target 共生成 29,768 token，W1 与 rescue 各生成 30,170 token。Target 与推测方法的随机输出不同属于不同解码路径；本批严格逐 token 对照的是 W1 与 rescue。

计时范围包含运行时和提案图构造、缓存准备、prefill、树验证、恢复、采样与图捕获。W1 有两条配对产生新图，记录 `graph_setup_ms` 分别约 1,073.8 ms 与 1,182.5 ms；rescue 对应约 1,460.0 ms 与 1,580.9 ms。两臂各自都记录 60 次 `unsupported_query_tokens` 回退。图准备配对没有从完整端到端结果中剔除，只在无新增图敏感性子集中单列。

结论适用于这 30 个来源、两个 prefix 和每个来源一个 seed。rescue 对 W1 的增幅较小，不能据此推断其他数据集、seed 或设备上的同等收益。
