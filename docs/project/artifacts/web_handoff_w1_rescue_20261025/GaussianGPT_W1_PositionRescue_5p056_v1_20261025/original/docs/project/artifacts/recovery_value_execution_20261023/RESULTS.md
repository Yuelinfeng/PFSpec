# 动态恢复选择：实现维护与验证结果

2026-10-23，已完成。原动态路径确有可避免的运行开销，现已移出正式解码。输出、实际选择、恢复调用和成本记录分别验证通过。当前证据支持“旧实现影响了性能判断”；动态策略相对固定单备用的新增收益仍需研究，不能由这次维护推定成立。

## 主要结果

三个既有开发来源、64/256前缀、512个新token上限，七种执行方式，两次独立进程。解码共168条，完整三维请求共84条。速度比定义为同输入参照耗时除以候选耗时，按来源等权取几何平均；大于1表示候选更快。这批数据用于实现核验，不作为新的来源外算法证据。

| --- | ---: | ---: |
| 新动态 / 旧动态 | 1.058868 | 1.046277 |
| 轻量解码器配原选择器 / 旧动态 | 1.057996 | 1.034124 |

新动态/旧动态的两个解码进程分别为1.062503、1.055246；完整请求分别为1.037764、1.054861。累计耗时方面，解码38.078257→36.074227秒，完整请求24.588990→23.566246秒。去掉冗余数据与空池回调后，配原选择器已经获得大部分解码提升。快速选择器的CPU用例耗时下降约22%–28%，完整执行中的独立收益较小，不能把局部CPU差异直接当作GPU收益。

同一新解码器内固定单备用/无备用为解码0.965592、完整请求0.937155。这三个开发来源包含首次建图与短EOS请求，不能替代此前20新来源的固定单备用结果。旧20来源结果及原始文件保留，也不与本轮比值拼接。动态策略是否能在来源外取得新增收益，仍未得到正向证据。

源码位于本机 `patches/recovery_value_20261023`：

- 新增 `test_selection_execution.py`、`test_adaptive_context.py`、`validate_execution.py`、`run_execution_review.py`、`verify_online_execution.py`。

## 计时与证据边界

独立运行对象、方法顺序轮换、第二进程来源起点轮换，首次图创建和实际选择成本计时。完整请求含生成、token保存、VQ、压缩Gaussian NPZ、六个384×384视图与PNG保存。模型加载、原始输入制作与16token预热在计时外。首次对象构造进入总墙钟，运行对象的分项计数从构造后开始。

原20来源上的变慢数值仍然描述当时的完整实现；它混合了策略效果与额外执行开销。此次维护给出了额外开销确有影响的实测证据，但只使用三个开发来源，不能推定新路径在原20来源或其他来源上的倍率，也不能直接认定动态策略已经优于强对照。

模型、信息、候选与决策目标保持。本轮没有训练神经模型、没有按这三个来源的结果调参、没有替换生产默认、没有运行自然全场景生成或原Target总倍率重测。下一步若继续研究动态策略，应先量化完整动作成本与决策价值，再使用新的来源作正式确认。
