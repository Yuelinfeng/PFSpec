# 概率策略独立核验

代码链路整体一致：模型只从 Target 概率标签学习，线上决策使用 Ranker 与前缀状态；模型导出和动作合法性都有对应证据。主要风险集中在两个线上输入量：验证轮里有可用备用时，`p_main` 估计偏低；EOS 的概率与分支成本没有单独进入线上价值公式。阈值规则还使用另一套较粗的成本代理，因此它们适合做对照，不代表同一成本目标下已经调优。

本次只读读取策略源码、已有训练/操作记录和策略模型，没有运行 GPU、远端任务或新速度数据。审阅范围和可复算数字记录在同目录 `independent_policy_review.json`。一次范围过宽的本地搜索曾打印出一条新速度记录；该行未汇总、未引用，也未进入以下核验。

## 数据划分与目标标签

`fit_probability.py:21-37` 只把 `target_mass_by_token` 放进训练目标 `y`，模型输入由 `probability_model.py:13-34` 从 Ranker 分数、候选名次、位置间隔、缓存位置和剩余预算构造。线上 `evidence_policy.py:6-43` 不读取 Target 标签或概率。

`fit_report.json` 记录按来源留出的 8 个训练来源和 2 个容量选择来源。我从原有 1908 行开发 `rounds.jsonl` 独立复算了 2332 个训练候选行和 716 个验证候选行，逐来源计数均与报告一致。`build_policy.py:24-28` 将阈值拟合样本限制到训练来源，操作成本记录的五个来源也都属于训练集；验证来源没有进入阈值计算。`policy_model.json` 本身未存来源清单或构建时的 split 文件路径，所以来源范围需要结合拟合报告和 builder 代码确认。

备用预测量表示 Target 策略对一个候选位置的无条件概率质量。对 point proposal `q=δ_main`，实际残差抽到备用 `b` 的联合概率就是 `p(b)`；代码把这项作为 `mass` 使用，在这一点上口径正确。

## 导出模型与线上输入

`probability_fit/probability_model.json` 有 64 棵深度 2 的树，特征顺序与 `FEATURES` 一致。`fit_report.json` 记录 sklearn 与纯 Python 推理在验证输入上的最大差为 0；我用保存的模型重算了候选行，按来源等权的备用 MSE 为 0.0351442，与报告相同。池化 MSE 为 0.0479666；两者权重不同，差异符合预期。根目录 `policy_model.json` 内嵌模型与 `probability_fit/probability_model.json` 完全相同。

容量选择指标只覆盖备用行，没有覆盖线上同样要用的 `p_main`。在两个验证来源中，217 个有备用候选的轮次里，Target `p_main` 均值为 0.81571，模型均值为 0.68346，MAE 为 0.31053、MSE 为 0.13213。没有备用候选的 184 轮误差明显较小，均值分别为 0.98428 和 0.97170。线上选择只发生在有候选的轮次，整体 `p_main` 指标会被无候选轮次稀释。这是会影响残差上限、拒绝概率门槛和价值排序的实际模型风险；本次没有重拟合或调参。

线上上下文由 `adaptive_decoder.py:159-189, 1080-1094` 构造，包含 `feature_vector` 所需字段。`test_evidence_policy.py:14-42` 在保存记录上完成了 9540 组完整/轻量输入比较，动作相同；加入标签与前缀 token 后动作不变；图形状不可用时返回空备用。解码器还会验证候选位置递增，并在 `_select_backup_ids` 中限制数量、去重及候选池成员关系。特征函数用固定 8000 归一化位置，当前词表匹配；改变位置映射时需重新训练。

## 成本公式、裁剪和 EOS

`predict()` 把单个候选概率裁剪到 `[0,1]`。`operation_value` 再把一个备用质量限制到 `max(0, 1-p_hat_main)`；这保证所选备用和主候选的估计质量不超过 1。它没有归一化所有备用概率，也没有从可用残差中扣除 EOS 概率。一次只选一个备用时，不归一化候选全集并非错误；EOS 未拆分则是近似。

成本以毫秒计，来自 33 个强制操作状态，覆盖五个训练来源，且没有验证来源。每个 `read_bucket` 使用路径差值的中位数；全局成本取四个桶中位数的中位数，因而每桶等权，不按各桶的重复次数加权。测量排除了选择器、采样和完整请求；正式墙钟会承担首次建图费用，而策略没有为首次建图单独估值。

操作记录的路径分解在 `analyze_operations.py:29-38`：主候选、备用命中、其他非 EOS 残差及 EOS 分别加权。线上 `evidence_policy.py:31-36` 把 EOS 也放进 `miss_extra_ms` 项，未使用 EOS 专属成本。已保存模型保留旧的 common-path 说明；当前 `build_policy.py` 已明确写出不预测 EOS 概率，并把剩余 EOS 质量计入 miss-path 成本。开发 1908 轮中有一条 `p_eos=0.0231982` 且备用可用。该轮无相同缓存位置的强制操作记录。用 bucket 512 的中位 EOS 路径差作敏感度估算，线上近似与替换 EOS 项的净值差约 0.000041ms，动作仍选同一备用；这只是桶级代入，不能说明其他状态也不受影响。

`build_policy.py:34-52` 为 score 与接受率对照选阈值，代理收益是 `target_mass × hit_saved − (1−target_mass) × common_extra`。线上 `operation_value` 使用 `p_hat_main`、miss 成本及当前桶成本。两者目标不同：阈值对照没有使用主候选概率、miss 项或 EOS 专项项，不宜称为与价值策略同一公式的最优控制。

## 结论边界

8/2 来源筛选、Target 标签用途、纯 Python 树导出和候选约束都有源码与已有记录支持。现有 2 来源容量选择显示模型对备用质量有一定预测信号，但 206 个验证上下文里模型策略只在 16 个上下文更换候选；来源等权实际质量为 0.07676，Ranker 首选为 0.07825。可用证据尚未显示更换候选能稳定提高质量。更关键的是，验证 `p_main` 指标在真实可选轮次上较弱，EOS 成本仅有近似，操作成本又不是完整请求时间。因此代码可执行与语义合法，不能单凭这些结果断定选择策略有效或会加速。
